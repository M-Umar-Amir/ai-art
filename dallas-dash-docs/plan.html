Coupons, game upgrade & mobile pathway

How a coupon earned in the game becomes a discount in the KFC ordering app with one database, single use, and a unique code every time. What we rebuilt in the game after studying Subway Surfers, and the step-by-step route to iOS and Android with React Native, Expo and EAS from a Windows PC.

Decisions we need from KFC

  • Accounts: which sign-in the KFC app already uses. The game must use the same user IDs, because that is what binds a coupon to a customer.
  • Offer terms: 15% off, $25 minimum, $5 cap, 30 days, 100,000 points are placeholders. Who funds the discount (brand or franchisee), and is it delivery only or pickup too?
  • Order system hooks: the checkout needs to call validate/reserve, and the payment and cancellation events need to call redeem/release/restore. We need to know who owns the ordering backend.
  • Legal review of the reward copy and terms. Dallas Dash is skill-based and needs no purchase, so it is not a sweepstakes, but KFC's counsel should confirm.

2 · Game → app coupons

Yes, one database

One Postgres database (for example Neon, provisioned through the Vercel Marketplace) with two schemas and one owner each. The game API writes game.*: accounts, verified runs and the points ledger. The coupon service writes rewards.*: coupons and their event history. The KFC ordering app never touches the tables. It calls the coupon service. One writer per table is what makes "a code works once" a guarantee rather than a hope.

Earning: points nobody can fake

  1. The server hands each account the seed for its next course. A run on any other seed is refused.
  2. The phone plays the course and records only the inputs (tick number + swipe), never a score.
  3. The game API replays the input log through the same sim.js with the account's own loadout from the database (multiplier, boards, keys, upgrade levels), and credits only the score the replay produces. A changed score, a reused run_id or more than 6,000 inputs is rejected.
  4. Points move only through game.point_ledger (+run, −coupon, +refund), so every balance can be audited back to the runs that earned it.

Issuing: a unique code every time

  • Atomic. The point deduction and the new coupon are written in one transaction, with the account row locked (SELECT … FOR UPDATE). You can never lose points without getting a coupon, or get a coupon without paying the points.
  • Idempotent. The claim carries an issueKey. A double-tap or a network retry returns the same coupon instead of minting two (tested).
  • Random, never derived. KFC-7K4Q-9M2P-XW3R-H is 12 symbols from a cryptographic random generator (60 bits, about 1.15 × 1018 possible codes) plus one check symbol. The alphabet drops I, O, 0 and 1. The code is not computed from the user ID or a counter, so no one can predict the next code. The database's UNIQUE index is the final guarantee: on the (practically impossible) clash, the service mints again.
  • Typo-proof. The check symbol rejects every single mistyped character (verified exhaustively), and 30 of 31 adjacent swaps, before any database lookup.
  • Stored safely. The service never stores the code in plain text. It keeps a keyed hash (HMAC-SHA256) for lookup, an AES-256-GCM encrypted copy so the owner can see it again in "My coupons", and the last 4 characters for customer support.
  • Limits. 100,000 points per code, at most 3 unused coupons per account, 30-day expiry.

Validation and verification at checkout

StepWhat the service checks
Cart preview
validate		The code is well-formed (check symbol). It exists and belongs to this signed-in user: someone else's code gets the same "not found" answer as a fake one, so the endpoint can't be used to fish for valid codes. It is active and not expired, and the subtotal meets the minimum. Returns the discount, 15% capped at $5 ($30 → −$4.50). Writes nothing.
Place order
reserve		Repeats every check, then locks the code to the order with one conditional update (… WHERE status='active'). If two checkouts race for the same code, exactly one wins (tested). Retrying the same order returns the same answer. A partial unique index allows only one game coupon per order.
Payment captured
redeem		Called by the order/payment service, not by the phone. Marks the coupon spent and records the discount taken. A webhook delivered twice is harmless.
Payment failed
release		Unlocks the code so it can be used again. A cron sweep also frees reservations older than 30 minutes, and expires old codes.
Restaurant cancels
restore		The coupon comes back with its original expiry, or a 7-day grace period if that date has passed.

To go live

  1. Provision Postgres (Neon via the Vercel Marketplace) and run schema.sql. Set COUPON_SECRET.
  2. Deploy the game API: the existing rules.js runs server-side unchanged, persisting to game.*. Turn TEST_GRANTS off.
  3. Connect sign-in to the KFC app's identity provider, so both apps share user IDs.
  4. KFC app: add a code field at checkout that calls validate, then reserve when the order is placed. Order service: call redeem, release and restore from the payment and cancellation webhooks. Schedule sweep every 5 minutes.
  5. Finance reporting: use coupon_events to report redemptions and discount dollars per store.

3 · Subway Surfers study

Subway Surfers is the reference endless runner: three lanes, swipe to dodge, jump and roll, trains to run on, and the inspector and his dog chasing you. Around that loop sit power-ups, a hoverboard shield, coins as currency, keys to revive, missions that raise a score multiplier, and rotating "World Tour" city themes. We mapped each feature to Dallas Dash. A few numbers deliberately differ, because here points turn into real money off food.

UI/UX changes

  • Home first, not a form. Tap-to-run fills the bottom of the screen, the runner jogs in the scene, the menu sits on the left and currencies on the top right, as in Subway Surfers. The coupon progress bar sits right above the play button, so the reward is always visible.
  • Minimal HUD. Score + multiplier, drumsticks, pause, power-up timers that shrink, and a hoverboard button with its count. The old stat rows and the long explanatory copy were removed from the run screen.
  • Feel. Faster pace, swipes that fire mid-gesture, screen shake, a white flash and vibration on crashes, a red edge glow during the chase, and pickup toasts named after real menu items.
  • Second chances. The "Save me!" prompt replaces the old 3-hearts system. That system was forgiving but flat, while one-hit crashes with paid revives create the tension that keeps runners replayable.
  • Progress after every run. The results screen shows the score, verified coupon points, best run and live mission bars, so there is always a next goal.
  • Accessibility. Keyboard controls everywhere, focus moves to the primary button in each dialog, reduced-motion is respected, and the touch targets are large.

Quality checks run

  • Fairness bot: a lookahead bot played 6 different courses for 3 minutes each (to top speed, about 6.6 km) without crashing or being caught, and an earlier 2-minute pass over 8 courses had zero stumbles. If a perfect player can survive, every pattern is escapable. Each run's full input log replayed to the identical score.
  • Rules tests (5): verified runs are credited; tampered, replayed and out-of-date runs are refused; revives spend only the keys the account owns; shop prices; coupon threshold, uniqueness and limit; old saves migrate.
  • Browser QA on a phone and a desktop viewport: full run → crash → revive prompt → results → "✓ verified", with zero console errors. Visual checks of every prop. These found and fixed two renderer bugs: long trailers vanished as you ran along them (no near-plane clipping), and the bridge deck was drawn as a wall across the road (a bug in the original build).

Rendering options. (A) Port the renderer to @shopify/react-native-skia: recommended, native 60 fps, same look. (B) For a fast MVP, wrap the existing web build in react-native-webview: shippable in about a week, but performance and app-store review are weaker. (C) Later, move to real 3D models with three.js via expo-gl / react-three-fiber if KFC wants character models and lighting.


Step by step on a Windows PC

  1. Install: Node.js LTS (22+), Git, VS Code. Optionally Android Studio for the Android emulator. Install Expo Go on a real iPhone and Android phone.
  2. Accounts: an Expo account (free), an Apple Developer Program membership ($99/year; it must be in KFC's or the franchisee's legal entity name for a branded app), and a Google Play Console account ($25 one-time).
  3. Create the project: 
    npx create-expo-app@latest kfc-dallas-dash
cd kfc-dallas-dash
npx expo install @shopify/react-native-skia react-native-reanimated react-native-gesture-handler \
  expo-audio expo-haptics expo-secure-store expo-router
npx expo start          # scan the QR with Expo Go on the phone
  4. Bring the game logic: copy sim.js and coupon-code.js into src/game/. Port scene.js to Skia and the HUD/menus to React Native components.
  5. Cloud builds: 
    npm i -g eas-cli
eas login
eas build:configure
eas build --profile development --platform android   # dev build for native modules
eas build --platform ios          # compiled and signed on Expo's Macs; EAS manages certificates
eas submit --platform ios         # to App Store Connect → TestFlight
eas submit --platform android     # to Play Console internal testing
eas update --branch production    # over-the-air JS fixes later
  6. Testing without a Mac: real iPhones via Expo Go during development, then TestFlight builds. Expo's cloud-hosted iOS simulator (EAS Simulator) was in limited preview as of September 2026.
  7. Backend: deploy the game API and the coupon service (section 2), and point the app at it. Sign in with the KFC app's identity provider. Add App Attest / Play Integrity to run submissions.
  8. Store readiness: privacy policy and data-safety forms, age rating, reward terms in the app, Sign in with Apple if any social login is offered, and haptics/sound settings. Keep drumsticks and keys earnable only: selling them for money brings in Apple/Google in-app purchase rules.
